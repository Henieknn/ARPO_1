### Шаг 5: Локальная сборка через терминал (CLI)

Полностью закрыл редактор Unity (проект нельзя открывать в двух экземплярах одновременно) и запустил автоматическую сборку из PowerShell в корневой папке проекта:

```powershell
& "C:\Program Files\Unity\Hub\Editor\6000.3.10f1\Editor\Unity.exe" -batchmode -nographics -projectPath "C:\Users\vragv\Desktop\Лабы\АРПО\ARPO1" -executeMethod BuildManager.BuildWebGL -quit -logFile build_webgl.log
```

Использованные флаги:
- `-batchmode` — фоновый режим без графических окон редактора;
- `-nographics` — отключение инициализации графического движка и видеокарты;
- `-executeMethod BuildManager.BuildWebGL` — вызов статического C#-метода сразу после открытия проекта;
- `-quit` — автоматическое закрытие Unity после завершения метода;
- `-logFile build_webgl.log` — перенаправление всего вывода консоли в отдельный файл.

Процесс идёт в фоновом режиме, консоль «замирает» на несколько минут.

## Контрольные вопросы

**1. Зачем в команде запуска CLI использовать флаг -nographics и какую роль он сыграет при переносе пайплайна на удаленный сервер в облаке?**

Флаг `-nographics` отключает инициализацию графического движка и видеокарты: редактор работает без создания графического устройства (NullGfxDevice). Это ускоряет запуск и убирает зависимость от GPU. При переносе пайплайна на удалённый сервер роль критическая: облачные CI-раннеры (например, ubuntu-latest в GitHub Actions) — headless-машины без монитора и видеодрайвера, поэтому без `-nographics` Unity просто не сможет инициализировать графику и сборка упадёт.

**2. Что произойдет, если запустить консольную сборку проекта, в настройках Build Settings которого не выбрана ни одна сцена игры? Какая строка кода обрабатывает эту ситуацию?**

Сборка не начнётся: метод `GetScenes()` вернёт пустой массив, после чего сработает защитная проверка `if (levels.Length == 0)` в методе `BuildWebGL()`. В лог выведется ошибка `[CI/CD] Ошибка: В Настройках Сборки (Build Settings) не найдено ни одной активной сцены!`, и процесс Unity корректно завершится с кодом возврата 1 (`ExitWithCode(1)`), что позволит пайплайну понять, что сборка провалилась.

**3. Почему класс BuildManager и его методы обязательно должны быть объявлены как public static?**

Флаг `-executeMethod` вызывает метод через рефлексию без создания экземпляра класса и без открытия графического интерфейса, поэтому требуется статический метод, доступный без инстанса (`public static void BuildWebGL()`). Класс должен быть public, чтобы механизм рефлексии редактора мог его обнаружить из сборки Editor, а метод — static, чтобы вызываться без объекта: при batch-запуске некому создавать экземпляры классов.

## Контрольные вопросы

**1. В чем заключается принципиальное различие между директивами run и uses в конфигурационном файле GitHub Actions?**

`run` запускает произвольную консольную команду или shell-скрипт прямо на раннере (например, `if [ -d "ProjectSettings" ]`). `uses` подключает готовый многоразовый экшен — переиспользуемый блок кода из репозитория или реестра (например, `actions/checkout@v4` скачивает код, `actions/upload-artifact@v4` сохраняет артефакты). `run` — свой сценарий построчно, `uses` — вызов готового плагина с параметрами `with`.

**2. Каким образом синтаксис YAML определяет вложенность и иерархию элементов, и какое ограничение накладывается на использование Tab?**

Вложенность в YAML определяется исключительно отступами из пробелов: каждый уровень вложенности — больший отступ, элементы списков обозначаются дефисом с пробелом (`- step`), пары «ключ-значение» — двоеточием с пробелом (`key: value`). Символ табуляции использовать строго запрещено — парсер YAML не понимает Tab и файл с табами в отступах вызовет ошибку парсинга, пайплайн не активируется.

**3. Какую роль играет директива needs в объявлении задач (Jobs) внутри файла main.yml, и что произойдет, если её не указать?**

`needs` задаёт явную зависимость: задача `mirror_repo` стартует только после успешного завершения `sanity_check` (упавший sanity_check блокирует зеркалирование). Без `needs` задачи одного workflow по умолчанию запускаются параллельно и независимо — зеркалирование началось бы одновременно с проверкой и могло бы продублировать в backup сломанный/некорректный код.

**4. Зачем в задаче зеркалирования (mirror_repo) используется параметр fetch-depth: 0 для экшена actions/checkout@v4? Чем это отличается от дефолтного поведения экшена?**

По умолчанию actions/checkout скачивает репозиторий с `fetch-depth: 1` — один последний коммит (shallow clone), что быстрее. Для зеркалирования нужна полная история: `fetch-depth: 0` забирает весь граф коммитов, поэтому в backup-репозитории воспроизводится идентичная история (хэши коммитов совпадают), а не одиночный снимок файлов.

**5. С какой целью секретные токены доступа сохраняются в разделе Repository Secrets вместо прямого указания строки токена в коде пайплайна?**

Секреты шифруются платформой и в логах маскируются (`***`), токен не попадает в открытый исходный код. Если зашить токен прямо в main.yml, его увидит любой, кто откроет репозиторий: он сможет писать в репозитории от вашего имени. Паттерн `secrets.BACKUP_TOKEN` подставляет значение в переменную окружения только на этапе выполнения и не раскрывает его в логах.

**6. Какое системное событие (триггер) настроено в разработанном пайплайне для автоматического запуска рабочего процесса?**

Триггер `on: push: branches: ["main"]` — workflow запускается автоматически при каждом `git push` в главную ветку main. Пуши в остальные ветки (LR1, LR2 и т.д.) пайплайн не запускают — только после попадания коммитов в main через Merge pull request.

**7. Что такое концепция Sanity Check и почему автоматическая проверка соответствия структуры должна выполняться до запуска зеркалирования?**

Sanity Check — быстрая базовая проверка «разумности» проекта: наличие служебных папок Unity и ключевых скриптов. Она выполняется первой и без неё зеркалирование не стартует (`needs: sanity_check`): если структура проекта сломана (нет ProjectSettings, удалены скрипты), в резервный репозиторий продублируется повреждённая версия, и резервная копия потеряет смысл — поэтому сначала верификация, потом дублирование.
